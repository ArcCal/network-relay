# Changelog

## Unreleased

- NF and RS GUI network observers ignore unchanged path notifications instead of restarting healthy proxy sessions. NF compares native path snapshots; RS compares primary-interface routing, address and link state while ignoring unrelated metadata. Real path changes still rebuild the connection, and manual Disconnect remains final.

- NF and RS GUI clients rebuild their connection after network path changes or persistent transport retry failures, waiting for the old listener to stop and backing off repeated failures. A two-second probe recovery window preserves healthy flows after an isolated stream reset. Manual Disconnect and Quit cancel recovery; gateway/quota replies preserve active flows. The sidebar and menu-bar node names are read-only; saved node and transport choices remain immediate in right-hand settings. Headless clients and servers are unchanged.

- NF and RS keep new servers in one unsaved form until Save succeeds, with only saved profiles in server menus. An explicit relay IP stays separate from SNI, certificate identity and HTTP host information; the relay domain needs no DNS records. Timeout retries and tunneled website/DNS traffic remain supported, with regression coverage.

- The all-target macOS builder also builds `network-relay-vless` for Linux x64 and arm64, verifies their static executable architectures, and includes both files in the artifact manifest and SHA-256 checksums.

- The all-target macOS builder defaults to a fresh complete checkout in `/tmp` on every run and a Desktop artifact folder named `YYYYMMDD-HHMMSS` in local time. Explicit source and output overrides remain available; existing output folders are preserved.

- Network Relay RS tests no longer require Linux `/proc` on macOS: descriptor duplication is checked under an exhausted descriptor allowance, and listener recovery is checked with a fresh client after the allowance is restored. The portable cancellation test also runs on macOS.

- Network Relay NF preserves native listener failure reasons, skips queued connections that failed before acceptance, and recreates a resource-exhausted SOCKS listener on the same resolved address. Recovery retries resource shortages, remains cancellable, and still reports permanent bind errors.

- Network Relay RS: accepted TCP sockets no longer duplicate their descriptor for reset support, and the SOCKS listener retries temporary descriptor shortages instead of stopping the client. NF and RS bound foreground SOCKS concurrency by the process descriptor allowance while reserving capacity for pending I/O and the application. Process and system limits are unchanged.

- network-relay-vless: retain usable DNS addresses when the other family returns an error, subtract reply-waiting time from cache TTLs, and require a matching successful DNS response for the startup probe. The Xray fixture pins localhost to its IPv4 listener so interoperability tests do not depend on host IPv6 preference.

- network-relay-vless: keep global tunnel, per-user and memory reservations charged while background writers drain and close their sockets. Regression tests verify reservation lifetime and that traffic on one UDP flow does not extend another flow to the same destination.

- network-relay-vless: bound writer draining and closing to five seconds after a tunnel ends, validate DNS answer owners and CNAME chains with their shortest TTL, and retain usable addresses when the other address family times out. Regression tests cover stalled writers, unrelated records, CNAME loops and TTLs, and partial A/AAAA replies.

- **network-relay-vless**, a new server in `network-relay-vless/`: network-relay with every tunnel carried through a downstream VLESS server (VLESS over a plaintext WebSocket, as an Xray-core `ws` inbound with `security: none` serves it). It is built on network-relay's library like network-relay-cf-masque and adds only an egress: TCP and UDP tunnels go to the addresses the destination rules allowed, names are looked up with DNS over TCP through the VLESS server, and nothing is ever sent directly. One TOML file holds the relay settings and a `[vless]` table; other transports, TLS, REALITY, flows and VLESS encryption are refused. Tested on Linux against Xray-core v26.10.31 built from source, with network-relay's `check` over HTTP/3, HTTP/2 and HTTP/1.1. Its README documents the limits: the plaintext downstream, Xray-core sniffing that replaces the checked destination unless `routeOnly` is set, a 200 before the destination is known, and no half-close. network-relay itself is unchanged.
- Network Relay NF's About page matches Network Relay RS: without a version it shows the source commit instead of `Unknown`, and the build time reads like RS (`2026-11-02 22:31:24 +08:00`, local time), with `Unknown` instead of `Not available` when missing. The `App.swift` line that shows it is not yet built on macOS.
- **The server log names the limit that refuses a tunnel.** A 503 `connection_limit_reached` was logged only with `log_requests` (otherwise at debug level), and an egress out of sockets or the relay's memory budget being used up was logged as `relay.max_tunnels reached`, so an operator could not tell which limit to raise. Such refusals now say what ran out (`out of capacity: the user-space socket limit was reached`, `out of capacity: the relay's memory budget is used up`), and without `log_requests` the first limit refusal on each client connection is logged at INFO with the user and the limit but not the destination; further ones on that connection stay at debug level, and the disconnect summary still counts them all. The status and Proxy-Status sent to the client are unchanged.
- **Destination connection attempts are paced and bounded** (RFC 8305 section 5). When an attempt failed, the next address was tried at once, so a name whose addresses all refused was tried 64 times in about 10 ms; section 5 forbids starting an attempt within 10 ms of the previous one. A failure now brings the next attempt forward to no earlier than 100 ms after the previous one started, the recommended minimum (64 refusing loopback addresses: 6.4 s). Attempts still pending are now capped at eight per connection: when another address is due, the oldest attempt is cancelled, and the next starts once it has ended. Before, one connection to a name with many unanswering addresses held up to 40 sockets (20 in a five-second test). The 250 ms delay while an attempt is pending and the connect timeout are unchanged, as is caddy-network-relay, which already paced and bounded attempts this way.
- network-relay-cf-masque: the WARP egress's user-space stack is no longer fixed at 64 sockets, which, shared with DNS and closing connections, forced `relay.max_tunnels = 48` and `max_tunnels_per_user = 32` and made one browser and a few apps run out of tunnels (503 `connection_limit_reached`). As in Xray and sing-box, whose MASQUE egress uses gVisor's stack with no fixed connection count, the limit now follows memory: as many sockets as fit, full (384 KiB each), in a quarter of it, between 64 and 4096 (682 at 1 GiB, 341 at 512 MiB). The socket buffers are zeroed allocations whose memory is committed only as data fills them. `[warp] max_sockets` sets another limit. Unless `relay.max_tunnels` is set, its memory-based default is kept to seven eighths of the socket limit, leaving room for DNS and closing connections; the example no longer lowers `max_tunnels` or `max_tunnels_per_user`. A new end-to-end test holds 300 TCP connections open at once through the real packet pump over HTTP/2 and HTTP/3; it fails with the former limit.
- Network Relay NF and RS: a refused request now shows the reason the relay gave in its Proxy-Status field (RFC 9209), for example `relay refused the request with HTTP 503 Service Unavailable: connection_limit_reached`, instead of always suggesting to check credentials, destination policy and the server template. Only printable ASCII is shown, at most 200 characters; without Proxy-Status the old text remains. Retry and failure handling are unchanged. Verified against network-relay and caddy-network-relay over HTTP/1.1, HTTP/2 and HTTP/3 with a per-user tunnel limit of two.
- Network Relay RS: after a relay crashed or restarted, new flows over HTTP/3 (and Automatic mode) failed for about two minutes. Such a server sends no CONNECTION_CLOSE and its new process cannot reset the old QUIC connection, so the client kept sending every new request on it until the 120-second idle timeout. The idle timeout is now 30 seconds with a keep-alive every 10 seconds, so a dead connection is replaced within 40 seconds, as the HTTP/2 PING keepalive already does; measured against network-relay and caddy-network-relay. A loopback regression test silences the path of an open connection and checks that the next flow uses a new one.
- Network Relay NF and RS: the vendored h3 no longer buffers a frame's whole declared payload before decoding it, so a hostile or faulty server could make the client hold any amount of memory (RFC 9114 section 10.5). As in the relay, frames of unknown types are discarded as they arrive, HTTP/2 frame types are refused from their header, and other frames but DATA over 64 KiB, four times the client's 16 KiB field section limit, close the connection with H3_EXCESSIVE_LOAD.
- Network Relay NF and RS show a unified main-window `Live Traffic` card for the actual running server. Live upload/download rates use SOCKS payload counters and measured monotonic intervals; idle, unavailable, reset and stopped states do not affect the connection. Both client design documents describe the telemetry, layout and lifecycle rules.
- **HTTP/3 frames are no longer buffered without bound.** The vendored h3 buffered the whole declared payload of every frame but DATA before decoding it, so one unauthenticated client could make the relay hold any amount of memory (RFC 9114 section 10.5): a HEADERS frame announcing 2^40 bytes, or an unknown frame type on the control stream, grew it by hundreds of MiB until a timeout. Frames of unknown types are now discarded as they arrive (section 9); a CANCEL_PUSH, GOAWAY or MAX_PUSH_ID longer than one varint is H3_FRAME_ERROR (section 7.1); other frames over 64 KiB, twice the 32 KiB header limit, close the connection with H3_EXCESSIVE_LOAD (section 8.1). Header sections between 32 and 64 KiB still get 431.
- **HTTP/1.1: a refused CONNECT closes the connection** (RFC 9931 section 8, which updates RFC 9112): the website's answer to a CONNECT without credentials, and every refusal, now carries `Connection: close`, so bytes a client sent after the request are never read as further requests. A connect-udp upgrade answered with anything but 101 closes the connection too (RFC 9931 section 6.3).
- HTTP/1.1 CONNECT takes its target from the request target in authority form only (RFC 9112 section 3.2.3); `CONNECT /path` with the target in Host, or an absolute URI, was accepted and is now refused with 400. An invalid Host value gets 400 (section 3.2).
- A malformed UDP proxying request over HTTP/2 or HTTP/3 (a `:scheme` other than https) is a stream error, as RFC 9298 section 3.4 requires: its 400 is followed by PROTOCOL_ERROR or H3_MESSAGE_ERROR (RFC 9113 section 8.1.1, RFC 9114 section 4.1.2), instead of an orderly close.
- QUIC clients must prove their address with a Retry once half of `max_connections` is taken, not only above 200 new handshakes a second: spoofed handshakes below that rate could hold the connection slots that HTTP/2 and HTTP/1.1 share (RFC 9000 section 8.1).
- An HTTP/3 error about an invalid header value names the field and the value's length, not the value, which could be a credential and reached the debug log.
- network-relay-cf-masque: an egress DNS timeout is reported as `dns_timeout` (504), and an egress out of sockets as `connection_limit_reached` (503); a datagram that no longer fits a shrunken WARP path is dropped instead of ending the flow, and a closing egress never reports an empty datagram. Its unused `nix` and `tracing-subscriber` dependencies and an unused module are removed.
- **network-relay-cf-masque is restored**, now built on this server instead of a private copy of it: it depends on this crate for the whole relay, its configuration format and the `passwd`, `identity`, `profile` and `check` commands, and on this repository's vendored h3, so it has the same behavior and parameters, current fixes included. Only its Cloudflare WARP egress is its own. It reads one standalone configuration file (this server's file plus `[warp]`); the separate WARP file, enrollment JSON and `migrate-config` are gone. Without `tunnel_ipv6` or `endpoint_v6` it warns at start and keeps running IPv4 only. On WARP loss open tunnels end with H3_CONNECT_ERROR or HTTP/2 CONNECT_ERROR, and it drains and exits.
- For it, this crate gains an `egress` interface: `server::Relay::with_egress` and `server::run_variant` send every tunnel's name lookups, TCP connections and UDP flows through an egress instead of the host network, with no fallback. network-relay itself uses none and is unchanged: its host-network code, output and help are as before. The helper commands moved from `main.rs` to the library (`cli`). `NETWORK_RELAY_TEST_EGRESS=loopback cargo test --test in_process` runs the integration suite through an egress; CI runs it too. The Linux server, macOS GUI and all-target build scripts build network-relay-cf-masque again for Linux x64 and arm64.
- Vendored h3: SETTINGS_H3_DATAGRAM and SETTINGS_ENABLE_CONNECT_PROTOCOL values other than 0 and 1 are a connection error of type H3_SETTINGS_ERROR (RFC 9297 section 2.1.1, RFC 9220 section 3); h3 accepted any value. Client-only extensions for the WARP egress (an outbound `cf-connect-ip` protocol, the draft-00 datagram setting, the peer's SETTINGS) are added; a server never uses them.
- GUI server and transport choices retry a failed connection and supersede an unfinished switch. Explicit Disconnect cancels queued restarts. Saving added or imported servers keeps an unchanged current server; imported changes to that server wait for Connect.
- **Network Relay NF: SOCKS GSS-API authentication (RFC 1961)**, the method every SOCKS5 implementation must support (RFC 1928 §3). With a Kerberos keytab configured, the proxy offers GSS-API only: context establishment, the protection-level subnegotiation, and integrity or confidentiality for the connection and every UDP datagram of its association; an optional principal list limits who is admitted. Without a keytab nothing changes. Tested with a stand-in mechanism and, with `scripts/test-socks-gssapi.sh`, real MIT Kerberos against both network-relay and caddy-network-relay over the transport emulator; GSS.framework and Network.framework on a Mac are not yet tested.
- The HTTP/3 header deadline starts at a request stream's first byte. Apple's QUIC connection group, which Network Relay NF uses, owns client stream 0 and never writes it; its first request on stream 4 implicitly opens stream 0 (RFC 9000 §3.2). The relay rejected that unwritten stream after ten seconds with `H3_REQUEST_REJECTED`, and in native tests the client's whole connection failed about then; the user later confirmed the native disconnect resolved with this fix and the client's probe-lifecycle fix, though which one Network.framework depended on was not isolated. Unwritten streams are now left open and do not count as requests for the idle timeout; streams with partial headers are still rejected after ten seconds.
- HTTP/3 control streams: a client's CANCEL_PUSH is a connection error of type `H3_ID_ERROR`, since the relay never sends PUSH_PROMISE and so has mentioned no push ID (RFC 9114 §7.2.3), and so is a MAX_PUSH_ID smaller than one received before (§7.2.7). The h3 library ignored both frames.
- Network Relay NF and RS: a write abandoned while waiting for its native completion no longer makes the next, shorter write report more bytes than it was given, which panicked in `write_all` (for example the first CONNECT-UDP capsule after an HTTP/1.1 request). The next write is now sent and counted on its own.
- Network Relay RS (app and headless): HTTP/2 shares one TLS connection across SOCKS flows and the readiness probe, as HTTP/3 already did. Each flow used to open its own TLS connection, which added a handshake (1 to 2 seconds remotely) to every new flow, and the 65th simultaneous flow was refused by network-relay's default limit of 64 connections per client address. A connection that received GOAWAY or failed is replaced for new flows while admitted flows continue on it. The shared connection's receive window is the protocol maximum, so flows whose data is not being read cannot stall the others; each flow still buffers at most its 2 MiB stream window. The client PINGs the shared connection every 20 seconds and replaces it when a PING goes unanswered for 20 seconds, so a network change that silently breaks it does not hold up new flows. HTTP/1.1 still uses one connection per flow.
- **Uploads to slow destinations no longer block a connection's other tunnels.** The relay releases a tunnel's flow-control credit only as its destination accepts the data, and each connection's receive window held just two stream windows: two uploads to destinations that stopped reading left every other tunnel on the HTTP/2 or HTTP/3 connection without credit, and on HTTP/3 even new requests could not be sent, because QUIC connection credit also covers request headers (RFC 9000 section 4.1). The connection receive window is now 4 MiB, four 1 MiB stream windows, by default. It stays within the connection's existing 8 MiB memory reservation, and the window per tunnel, and so single-tunnel upload speed, is unchanged. Only flow-control window sizes changed, which RFC 9113 section 6.9 and RFC 9000 section 4 leave to the receiver; no frame, setting or response changed.
- Network Relay NF: the shared HTTP/2 connection's receive window is the protocol maximum instead of 5 MiB, so three downloads whose data is not being read can no longer stall every other flow on the connection. Each flow still buffers at most its 2 MiB stream window.
- Network Relay RS and NF: the minus (-) button deletes the selected server. A saved server is removed from the saved settings at once, after a confirmation, and deleting the connected server moves the connection to its neighbor in the list; other unsaved edits are kept. It used to remove the server from the form only, so nothing changed until Save. Saved server and transport choices still apply immediately; unsaved or newly imported servers still need Save before they can be chosen.
- Network Relay RS keeps NF's per-server admission probe target (`probe_target`) when importing, uses it to connect, including headless, and writes it back on export and in its client configuration, so NF exports move through RS without losing it. Settings saved before this keep the default 1.1.1.1:53.
- Build scripts no longer leave restrictive permissions behind: when a build or packaging script ends, successfully or not, every folder in its source checkout and its results is mode 777, so other users and file synchronization tools such as Syncthing can use them. File modes are unchanged. The README lists every build script.

H2O reference limitations and failed original-tool close checks remain documented. **Apple system-client acceptance, impaired-network tests and long WAN soak remain unverified.**

## 1.3.0 — 2026-10-06

- **HTTP/3 cancellation codes**: when the relay ends a request or tunnel early, the client now gets the intended HTTP/3 error code in both directions (RFC 9114 §4.1.1). The STOP_SENDING half used to lose its code whenever a read was pending, which is nearly always for a tunnel, and clients saw code 0, which HTTP/3 does not define, instead of `H3_REQUEST_CANCELLED`, `H3_CONNECT_ERROR`, `H3_DATAGRAM_ERROR` and so on (vendored h3-quinn fix). A request the client cancels while it is being authorized or connected is now cancelled with `H3_REQUEST_CANCELLED` rather than dropped, and a request whose headers exceed 32 KiB gets its 431 with STOP_SENDING `H3_NO_ERROR` (RFC 9114 §4.1).
- **HTTP/3 requests whose headers do not arrive within 10 seconds are rejected** with `H3_REQUEST_REJECTED`, so the client may retry them; the stream used to end with a FIN and no response, which reads as a truncated response (vendored h3 `resolve_request_before`).
- **GOAWAY cannot hold a connection open**: sending it now gets one second. The control stream it travels on is flow controlled, so a client that granted no more credit kept a connection the relay was closing (idle, or on shutdown), and its connection slot, for as long as it kept the connection alive.
- `:protocol` in HTTP/2 and HTTP/3 extended CONNECT is matched without regard to case (RFC 9110 §7.8), as `Upgrade` already was on HTTP/1.1: `CONNECT-UDP` was answered with 501. HTTP/3 `TE: trailers` is likewise accepted in any case.
- CONNECT-UDP paths whose `target_host` carries an IPv6 address with unencoded colons (`/.well-known/masque/udp/2001:db8::1/443/`) are understood; RFC 9298 §2 asks clients to percent-encode them, but `:` is valid in a path and names the same address. Such requests used to get the website's 404.
- Verified against independent implementations: quic-go and masque-go (HTTP/3 CONNECT and CONNECT-UDP), curl (HTTP/1.1 and HTTP/2 CONNECT); see `docs/review-2026-10-05.md`.
- **Anonymous connections can no longer lock devices out.** Version 1.2 reserved 8 MiB of the shared buffer budget for every TCP or QUIC connection as it was accepted, before TLS: on a 1 GiB server, 64 idle connections from a single address (the default `max_connections_per_ip`), or a trickle of spoofed QUIC handshakes, used up the budget, and every device was refused. A connection now reserves its windows only when it opens its first tunnel, i.e. once it has authenticated; until then it is bounded by the connection limits and timeouts.
- **Usable capacity on small servers.** A tunnel reserves 512 KiB, which covers the relay's own buffers for it; kernel socket buffers are fixed per socket and bounded system-wide by Linux, and are no longer counted as 16 MiB per tunnel. The default `max_tunnels` is 512 at 1 GiB (was 16) and 2048 at 4 GiB (was 64). The capsule queue towards the device is now also bounded in bytes (128 KiB), and HTTP/3 datagram payloads are copied out of QUIC's receive buffers, so these bounds hold.
- **More concurrent tunnels per connection.** Devices carry every relayed TCP connection and UDP flow on one connection, and version 1.2 allowed only 32 streams on it, so further connections stalled until another ended. HTTP/3 now allows 100 (the minimum RFC 9114 §6.1 recommends) until the connection authenticates, then 1024; HTTP/2 allows 256.
- `max_connections` now defaults to available memory at 512 KiB per connection (256 to 16384; 2048 at 1 GiB) instead of a fixed 16384. An explicit value is used as given.
- **Slow readers**: a website or refusal response that makes no progress for 30 seconds because the client does not read it is abandoned (HTTP/2 `CANCEL`, HTTP/3 `H3_REQUEST_CANCELLED`, HTTP/1.1 closes the connection), so visitors cannot hold connections, buffers and slots open indefinitely. HTTP/2 website answers drop the unread request body before responding and send the page without copying it.
- The listener on the IPv6 wildcard (`listen = "[::]:443"`, the default) now accepts IPv4 clients even where `net.ipv6.bindv6only = 1`, which previously made IPv4 devices fail silently, and falls back to IPv4 only on a host booted without IPv6 instead of failing to start.
- HTTP/3 requests carrying connection-specific header fields (`Connection`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding`, `Upgrade`, or `TE` other than `trailers`) are malformed and reset with `H3_MESSAGE_ERROR` (RFC 9114 §4.2), as HTTP/2 already did (vendored h3 patch).
- HTTP/3: datagrams that arrive before their stream is set up are held for at most one second (RFC 9297 §2.1); when the relay ends a UDP flow itself (idle timeout), it stops the device's sending with `H3_NO_ERROR` rather than the undefined code 0.

## 1.2.0 — 2026-10-05

- Rust relay audit: expiry changes on reload invalidate authenticated snapshots and cached credentials; HTTP/1.1 upgrades retain connection admission and shutdown tracking; UDP stream read failures trigger error cleanup instead of normal FIN; cancelled keyed waiters refund their map entries. HTTP/1.1 now enforces the connection idle deadline, and HTTP/3 setup has a handshake/setup deadline.
- Network and website buffer capacity is shared across TCP, QUIC, tunnels and retained website response bodies and sized from host and visible ancestor cgroup memory limits. Transport windows, send buffers, kernel TCP buffers and datagram queues are bounded together; the default tunnel allowance is now 16 MiB per tunnel, with no 512-tunnel minimum. See `docs/config.md` before upgrading a small VPS. Log queues are reduced to 1024 lines per writer, and password-hash concurrency is also bounded by available memory.
- One-time profiles remain one-time across overlapping reload snapshots. Published files and consumption history are bounded; `.publish` parent symlinks cannot expose files outside the website. Empty service selections in `global-profile.py` are rejected instead of generating an all-traffic Apple profile. Domain-list reads have a 16 MiB limit.
- Installer prepares the device profile and validates a staged certificate pair before changing the account/service. Profile and certificate updates participate in rollback, which now restores original owner, group and mode. The renewal hook stages both certificate files before replacing either. Client identity profiles request `KeyIsExtractable=false` on macOS; original profile and PKCS#12 copies still contain the private key and must be protected. Invalid XML characters in embedded identity passwords are rejected.
- Destination protection fails closed after an interface-address refresh error and caches the failure to bound retries. The default blocked ranges also include IANA's dummy IPv6 prefix `100:0:0:1::/64`.

- **The service no longer runs as root** (G-8): the systemd unit runs it as user `network-relay`, with only `CAP_NET_BIND_SERVICE`. It reads the configuration (mode 640) and a copy of the TLS certificate in `/etc/network-relay/tls` through its group, since certbot's own key can be read by root alone. The new `deploy/certbot-hook.sh` makes the copy after every renewal and reloads the relay. The installer creates the user, sets up the copy, moves installations from earlier versions over to it, and refuses a `--cert`/`--key` the user cannot read, saying how to allow it. `profile --publish` gives the file the owner of the `.publish` directory, so the relay can read profiles that root publishes. **Manual installations** that switch to the new unit file must do the same (README, manual install step 8).
- CI: GitHub Actions are pinned to commit SHAs instead of movable tags, and cargo uses the committed `Cargo.lock` exactly (`--locked`) (X-10).
- **A reload applies new destination rules to open tunnels**: a TCP connection or UDP flow whose connected address or port the reloaded `blocked_destinations`, `blocked_ports` or own-address rule blocks is closed, as tunnels of removed users already were (R-9).
- **Password checks no longer share threads with name lookups** (R-10): hashing runs on threads of its own, one per hashing slot, instead of tokio's blocking pool, where slow lookups could hold it up. Name lookups are limited to 256 at once and 32 per user, so one user cannot delay everyone else's; a lookup keeps its place until the system resolver returns, even after the 5-second timeout gave up on it, so abandoned lookups cannot pile up threads.
- Removed unused code and dependencies: the direct `rustls-pki-types` dependency (rustls's `std` feature already provides it), unused `hyper-util` features (`server-auto`, `http1`, `http2`), never-read URI template accessors and fields, an unused datagram-size query and certificate PEM field, and helpers that only tests used are now compiled for tests only.
- **UDP flows close when the destination is unreachable** (RFC 9298 §3.1 MUST): an ICMP Destination Unreachable reported on the target socket (port, host or network unreachable) now ends the flow with `H3_CONNECT_ERROR`/`CONNECT_ERROR` instead of keeping it open until the idle timeout. Errors that concern one datagram (too large for the path, a full queue, a local firewall rule) still only drop it.
- **Graceful shutdown**: on SIGTERM the relay stops accepting connections, sends GOAWAY on every HTTP/2 and HTTP/3 connection (RFC 9113 §6.8, RFC 9114 §5.2), lets open requests finish for up to 5 seconds, then closes QUIC connections with `H3_NO_ERROR`. Requests arriving after GOAWAY are rejected with `H3_REQUEST_REJECTED`, so clients may retry them.
- The HTTP/3 GOAWAY identifier is the first request not processed, as RFC 9114 §5.2 defines it (vendored h3 patch); it was the last accepted one, the HTTP/2 meaning, which invited clients to retry a request that had been processed.
- **HTTP/3 requests are validated as RFC 9114 requires** (vendored h3 patch): a pseudo-header field twice, `:status` in a request, a classic CONNECT with `:scheme` or `:path` or without `:authority`, an extended CONNECT without `:scheme`, `:path` or `:authority`, `:protocol` on another method, and other requests without `:scheme` or `:path` are malformed and reset with `H3_MESSAGE_ERROR` (§4.1.2, §4.3, §4.3.1, §4.4; RFC 8441 §4). An extended CONNECT with a protocol the relay does not implement (`connect-tcp`, `connect-ip`, `websocket`) now gets **501** with `Proxy-Status` once authenticated, on HTTP/2 and HTTP/3, instead of a stream reset or the website.
- **Malformed UDP proxying requests get 400** once authenticated (RFC 9298 §3.2, §3.4): an HTTP/1.1 `Upgrade: connect-udp` that is not a GET with `Connection: Upgrade` (previously answered by the website with 200), and an extended CONNECT for `connect-udp` whose `:scheme` is not `https`. `Upgrade` in an HTTP/1.0 request is ignored (RFC 9110 §7.8).
- A datagram on an HTTP/3 request without datagram semantics (a website request) whose receive side has already closed is dropped silently instead of resetting the request (RFC 9297 §2.1).
- Proxy-Status error types and status codes follow RFC 9209 §2.3: a blocked address is `destination_ip_prohibited` with **502** (was 403), a name without addresses is `dns_error` (was `destination_not_found`, which is for gateways without configuration), an unreachable network is `destination_ip_unroutable` (was `destination_unavailable`). Blocked ports and revoked users stay `http_request_denied` with 403. `check` explains blocked destinations either way.

Fixes for the High and Medium findings of the 2026-10-04 assessment:

- **Authentication can no longer be used to exhaust the server.** Only new credentials cost a hash, and those checks are limited per client address (IPv4 or IPv6 /64: one per second after a burst of 30) and per connection (four at a time); requests over the limits get the website. Requests with the same new header wait for one check, without counting against the connection's limit. Verified credentials are bound to their connection, stay cached while in use (sliding 10 minutes), and survive reloads for users whose entry did not change.
- Generated passwords get a fast hash (`$pbkdf2-sha256$i=1000,l=32$...`, the same format the Caddy plugin uses); chosen ones keep Argon2id, whose parameters are now bounded (at most 64 MiB, 10 passes, 4 lanes). `passwd --stdin --fast-hash` takes a random secret from elsewhere.
- **The server's own addresses are blocked** (`relay.block_own_addresses`, on by default), its public addresses included, which the list of ranges could not cover. IPv6 addresses that carry an IPv4 address (IPv4-compatible, NAT64, 6to4, Teredo) are also checked by that address. Added `192.88.99.0/24`, `2001:2::/48`, `2001:10::/28`, `2001:20::/28`, `3fff::/20` and `5f00::/16` to the default blocked ranges.
- **Limits per user and per client**: `max_tunnels_per_user` (512), optional `max_bytes_per_second_per_user` and `max_udp_packets_per_second_per_user`; `max_connections` (16384) and `max_connections_per_ip` (64), with QUIC connections refused before the handshake and Retry when handshakes arrive faster than 200 a second; `idle_timeout_secs` (300; 30 for connections that never authenticated). Without `max_tunnels`, the default is sized from memory (1 to 20000 at 16 MiB per tunnel) instead of a fixed 20000, and the open-file limit is raised to fit.
- **Logging no longer blocks the relay**: lines go through a bounded queue to a writer thread and are dropped when the journal or disk cannot keep up; failed authentications are logged at most about five a second, with a count of those left out.
- **QUIC path MTU**: connections start at 1200 bytes and probe up to 1452 (DPLPMTUD) instead of starting at 1350, so the handshake works on any path and full-size relayed QUIC packets fit as soon as the path allows.
- **Credentials**: users can have `expires` (their tunnels close then) and `certificate_sha256` for client-certificate authentication (`[tls] client_certificates = true`). `network-relay identity` creates the certificate and a PKCS#12 file, and `profile --identity` puts it in the profile with `PayloadCertificateUUID`. `profile` and `check` warn when `--password` is given on the command line.
- `profile --ddm` writes a declarative device management declaration (`com.apple.configuration.network.relay`), with `--identity-asset` for an MDM identity asset.
- `profile --publish` now writes into the website's hidden `.publish` directory; each file is served once, within 15 minutes, and never again after a reload. Expired files are removed by the next `--publish`. Profile signing with openssl or `security cms` is documented.
- `profile` warns about `UIToggleEnabled` false, profiles that rely on `MatchFQDNs` alone, and excluded host names outside every matched domain. `deploy/global-profile.py` now defaults to `--ui-toggle-enabled true`, so the user can switch off a relay that is down.
- **Installer**: keeps no copy of the password. A new installation's profile is published once behind a printed link (or written to `--profile-out`), the generated password gets the fast hash, and the installation's domain, port and user name are recorded in `/etc/network-relay/install.json`, so upgrades need neither the profile nor the password. Installations from earlier versions are upgraded from their `device.mobileconfig`, which the installer then tells you to delete.

- When loading the website, the file actually opened is checked, so a parent directory swapped for a symlink between the check and the open cannot expose files outside the site.
- HTTP/1.1 requests with no `Host` or more than one `Host` get 400 (RFC 9112 §3.2, RFC 9298 §3.2).
- If a request expanded from `relay.udp_template` does not parse back to the original target, configuration loading and profile generation fail outright instead of silently treating UDP requests as website requests.
- `serve --check` reports an error for a certificate that has expired or is not yet valid.
- Installer: `--cert`/`--key` are saved as given (Let's Encrypt `live/` symlinks are not resolved); an upgrade keeps the existing installation's certificate setup instead of suddenly switching to certbot; a `--cert`/`--key` that differs from the existing configuration is refused rather than silently ignored; the startup check accepts any HTTP response (without `[web]` the home page is a 404); `procps` is installed.
- The one-step installer also supports Debian 12 (bookworm) x86_64.
- The installer's `apt-get` waits for the dpkg lock (up to 30 minutes), so it no longer fails outright on a freshly booted VPS that is running automatic updates.
- CI: in the arm64 tests, child processes started by tests also find the dynamic linker through qemu.
- `passwd --stdin`, `profile` and `check` no longer echo the password when prompting for it in a terminal.
- The error code used when a UDP flow ends early now depends on the cause: a malformed message, a failed target socket, and cancellation or revocation use `H3_MESSAGE_ERROR`/`PROTOCOL_ERROR`, `H3_CONNECT_ERROR`/`CONNECT_ERROR` and `H3_REQUEST_CANCELLED`/`CANCEL` respectively; previously all were treated as malformed messages.
- On an HTTP/3 TCP tunnel, datagrams received after the device has sent FIN are silently dropped (RFC 9297 §2.1) instead of resetting the stream.
- HTTP/1.1 `Connection` and `Upgrade` are parsed as token lists; HTTP/2 rejects a `Date` on responses.
- Added `deploy/global-profile.py`: builds a `.mobileconfig` from a service domain list (`deploy/domains/global-services.txt`) and the gfwlist, using only the standard library and `network-relay profile`; it has automated tests.
- If the listener or certificate-reload task exits unexpectedly, the process now exits with an error (and systemd restarts it) instead of carrying on with a listener missing; signal handlers are registered before the listeners start.
- A reload no longer gives the decoy website's 404 to requests that are in their first authentication and whose user did not change; failed authentication results can no longer evict authenticated entries from the cache.
- Dangling or looping symlinks in the website directory no longer make the whole website fail to load.
- The HTTP/1.1 request header buffer is limited to 64 KiB (previously hyper's default of about 400 KiB), close to the 32 KiB header limit of HTTP/2 and HTTP/3.
- In environments without IPv6 loopback, the no-fragmentation test skips its IPv6 part; added a regression test that successful HTTP/1.1 responses carry no framing headers.
- Added a source-build installer for Debian 13 x64: automatic certificates, renewal, systemd, configuration import, self-check and rollback on startup failure; ships a Google/AI/X domain preset, and the private device profile is generated separately and never added to the repository.
- Fixed cancellation after HTTP/2 half-close, idle HTTP/3 STOP_SENDING, connection loss, and user revocation while the response is blocked by flow control, so target connections and tunnel slots are released promptly.
- Trailing HEADERS on CONNECT are rejected as the protocols require; fixed empty HTTP/3 DATA being taken as the end of the stream and truncated DATA being taken as a normal close. The local patches to dependencies and their origin are recorded in `vendor/*/PATCH.md`.
- Large capsules with an unknown UDP context are discarded as a stream; a closed write side is no longer treated as ordinary packet loss, blocked write tasks exit within a bound, and a steady stream of incoming packets no longer holds off cancellation and timeouts.
- Fixed matching errors when a URI template separator appears in the host name; tightened validation of configuration, Argon2 hashes, and profile XML and domain names.

## 0.1.0

First release.

- **Relay server**: TCP relaying (classic CONNECT) and UDP relaying (CONNECT-UDP, RFC 9298) over HTTP/3 (UDP 443), HTTP/2 and HTTP/1.1 (TCP 443), implemented the way Apple's network relay uses them.
- **Authentication**: user name and password (HTTP Basic, `Authorization` or `Proxy-Authorization`); the server stores only Argon2id hashes; authentication results are cached; users deleted in a reload are disconnected immediately.
- **Decoy website**: requests without a password see an ordinary website; missing files under `/.well-known/` get 404.
- **Destination restrictions**: internal networks, the server itself, metadata services and similar addresses are blocked by default, checking every address a domain resolves to; port 25 is blocked by default.
- **Error information**: failed requests that passed authentication carry `Proxy-Status` (RFC 9209).
- **`network-relay profile`**: generates profiles for iPhone, iPad and Mac, which can be put straight on the decoy website and installed by opening them in Safari (`--publish`).
- **`network-relay check`**: tests TCP and UDP relaying over all three HTTP versions.
- **`network-relay passwd`**: creates users and passwords.
- systemd unit (keeping only the permission to bind port 443), sysctl settings for UDP buffers, GitHub Actions builds for x86_64 and arm64.
- Interoperability tested with curl and quic-go's masque-go; **not yet tested on real Apple devices**.
