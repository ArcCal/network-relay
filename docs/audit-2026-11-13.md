The DNS retry measurement is a local debug fixture, not general DNS latency or
WAN throughput. The follow-up repair passes the parent's existing absolute
deadline to the VLESS resolver. Reaching that deadline completes a timeout
failure and caches it for one second; caller cancellation and a timeout while
waiting for admission still do not create a cache entry. A slower failed lookup
does not replace a fresh successful answer from another lookup. The five-second
total budget, 2.5-second per-resolver bound, sequential attempts and admission
limits are preserved. A subsequent repair prefers the last successful resolver
and resumes after a deadline-interrupted attempt on the next uncached lookup.
This prevents repeatedly paying for a dead first resolver and lets later
configured resolvers be reached across bounded attempts. A single lookup still
cannot try every silent resolver within five seconds. See the
[follow-up evidence](dns-deadline-validation-2026-11-13.md).

## Performance factors retained for capacity planning

| Factor | Consequence and decision |
| --- | --- |
| Receive windows and memory reservations | Main defaults use a 1 MiB stream window and 4 MiB shared connection window. Window/RTT is a useful BDP model, not a measured WAN ceiling. Increasing windows without increasing reservations can reintroduce head-of-line starvation or memory overcommit. No blind increase was made. |
| Fixed kernel TCP buffers | Explicit client/target buffer caps limit memory but can constrain high-BDP paths and disable Linux autotuning. No universal larger default is justified by loopback measurements. |
| PMTU and nested QUIC | Initial 1200-byte QUIC packets and discovery can delay larger inner packets. Oversized negotiated DATAGRAMs remain drops, not reliable Capsule retransmissions. |
| Connection reuse | H2/H3 clients share connections and have independent stream cancellation; H1 pays a separate TLS connection per tunnel. Reuse/GOAWAY/stalled-flow tests remain necessary. |
| Client UDP transport | Both clients use reliable Capsules. Loss-induced stream head-of-line blocking remains; these clients do not gain native-DATAGRAM latency from the encoder optimization. |
| DNS | System resolver slots remain held until non-cancellable resolution returns. VLESS TTL-aware caching reduces repeated completed failures; no guessed-TTL main resolver cache was introduced. |
| Hashing and logs | Argon2 remains intentionally expensive for chosen passwords. Bounded logging avoids unbounded retention but verbose formatting/polling still costs CPU. |
| WARP stack | 256 KiB receive/128 KiB send TCP buffers, one outer generation, 1280-byte stack MTU, bounded queues and closing sockets constrain BDP and churn. Increasing them changes resource admission. |
| VLESS transport | One downstream TCP/WebSocket per flow and reliable UDP encapsulation add setup RTT and loss-induced head-of-line blocking. No direct fallback or weaker destination checks were introduced. |
| Aggregate client queues | Per-session/flow queues are bounded but their combined payload capacity can still be large. No unmeasured global budget redesign was combined with these fixes. |

An isolated exact-source inner-stack experiment compared the current WARP
buffers with 1 MiB receive/512 KiB send buffers. All 18 trials preserved exact
8 MiB hashes in both directions, directional EOF/FIN, zero resets/drops and
natural cleanup. Larger buffers did not show a consistent throughput benefit
at configured 50/100 ms RTT, while requiring four times the buffer memory; the
unchanged one-GiB socket-budget formula falls from 682 to 170 sockets. No larger
default was adopted. New-flow CUBIC growth, scheduling delay tails and shared
CPU load limit interpretation. This is an inner-stack simulation rather than a
Cloudflare or full-relay WAN benchmark; see `bdp-experiment.md` for raw data.
