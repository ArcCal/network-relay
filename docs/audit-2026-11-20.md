# Network Relay and Caddy Network Relay audit, 2026-11-20

The release baselines were Network Relay `bc6940a` and Caddy Network Relay
`6963508`. Network Relay `33ee4fc` changed the HTTP Date implementation.
Caddy `e770748` changed Capsule reads and `d7483b1` corrected QUIC path
discovery. Network Relay `ad82fe8` fixed a reproducible global TUN startup
failure. Its subsequent VLESS work covers cache eviction (`9e7b465`),
concurrent lookups (`33e179a`) and independent failover deadlines (`4b30aed`).
The combined program snapshot `abe6d90` also includes the WARP DNS cache
(`650e806`), Swift NF and TUN log handling (`6e70668`) and the RS log view.
The final Network Relay program is `d5bd2b7`. Its WARP TCP fix honors
valid peer window changes for queued data before the closing FIN is sent.
The final Caddy audit branch is `8acd7b2`.
Caddy `d7483b1` includes the dependent-module advisory check,
the native installer correction and the QUIC datagram size fix. The TUN validation branch runs the
same application code with a disposable macOS helper workflow. The shipping server platforms are Linux x86-64
and Linux arm64. macOS and iOS are client platforms. Test counts overlap across suites run in
more than one environment.

### Standards and trust boundaries

The Apple profile and declarative management schemas require RFC 9298 URI
templates for UDP and H2/H3 relays supporting TCP and UDP CONNECT. The server
review checked response dates against RFC 9110 section 6.6.1, Capsule framing
and unknown types against RFC 9297, and context handling, datagram boundaries
and the 65527-byte ceiling against RFC 9298. The tests preserve authentication,
certificate verification, destination policy, bounded memory and correct
termination for incomplete Capsules. [Apple Relay payload](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.relay.managed.yaml)
[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-6.6.1)
[RFC 9297](https://www.rfc-editor.org/rfc/rfc9297)
[RFC 9298](https://www.rfc-editor.org/rfc/rfc9298#section-6).

| Server decision | Governing behavior and check |
| --- | --- |
| VLESS and WARP DNS caching | RFC 1035 section 3.2.1 limits TTL zero to the transaction in progress. RFC 2308 section 5 derives negative TTL from the SOA. RFC 9520 section 3.2 requires a separate resolution-failure cache. The tests check expiry, missing or unrelated SOA, distinct failure status and bounded storage. |
| QUIC flow control | RFC 9000 sections 4 and 19.9-19.13 assign credit to the receiver. Tests check acknowledged ranges and both connection and stream limits before attributing a stall. A server cannot send past the limit advertised by its peer. |
| CONNECT-UDP size and return path | RFC 9297 and RFC 9298 preserve datagram boundaries and specify size handling. RFC 8899 path probes require acknowledgment. The tests compare both endpoints' byte counts, exact payloads, asserted path size and drop reports. |
| WARP CONNECT-IP egress | RFC 9484 governs the egress tunnel and RFC 9221 sets the peer-advertised limit for QUIC DATAGRAM frames. The local peer exercises address assignment, H2 Capsule and H3 datagram carriage, MTU changes, IPv4 and IPv6. |
| TCP inside WARP | RFC 9293 section 3.8.6.3 and RFC 5681 section 4.2 recommend acknowledging at least every second full-sized segment or equivalent data, and impose a maximum delay. Packet, hash, FIN and socket-release tests accompany the performance comparison. |
| TCP close with queued response bytes | RFC 9293 sections 3.10.4 and 3.10.7.4 require queued sends ahead of FIN and define acknowledgment processing. Section 3.8.6.1 defines zero-window probing. The packet tests check reopening, retraction, scaling, sequence validation, byte order and FIN acknowledgment. |
| Apple transport selection | The Apple Relay payload and declarative Relay configuration permit either H2 or H3, or both. Each configured endpoint must support proxying TCP and UDP. The generated and derived profiles keep authentication, trust anchors, pins and domain settings. |

### Local performance comparisons

Rust previously formatted a new GMT string for each response. A per-thread
header keyed by the current wall-clock second preserves second precision and
responds to a backward clock adjustment. Ten alternating pairs of optimized
500000-call runs measured medians of 647.3 and 103.4 ns per call. The boundary
test covers repeated calls, a day change and a backward clock step.

Caddy now lets the existing 16 KiB reader deliver a small Capsule to its
synchronous consumer. The first larger datagram allocates a reusable buffer.
The old and candidate readers ran the same compiled Go benchmark cases, on a
single CPU with one Go worker, in alternating order with four samples per arm.
Each operation starts one stream. Allocated bytes count the reader and payload
storage and do not represent process RSS.

| Capsule workload | Before ns/op | Candidate ns/op | Before B/op | Candidate B/op |
| --- | ---: | ---: | ---: | ---: |
| Idle reader | 3737 | 3911 | 16528 | 16528 |
| Unknown Capsule | 3914.5 | 3940.5 | 16528 | 16528 |
| Empty datagram | 4090 | 4711 | 16528 | 16528 |
| One 1200-byte datagram | 12663 | 3896 | 82064 | 16528 |
| 64 consecutive 1200-byte datagrams | 20106 | 7103.5 | 82064 | 16528 |
| One 65527-byte datagram | 22761.5 | 20602.5 | 82064 | 82064 |

The allocation reduction is repeatable for small-only streams. The timings
include scheduler and garbage collector variability. Installed-device or WAN
throughput needs separate measurements.

### Dependency checks

All 11 tracked Cargo lockfiles were checked against RustSec database revision
`f291af9b1cc0d21dfcea1709d6b037963cef262b`. Two locks selected heapless 0.9.3,
with nine unsoundness advisories, RUSTSEC-2026-0574 through RUSTSEC-2026-0582.

database and a new scan of all eleven lockfiles at `abe6d90` also reported
zero entries in the vulnerability category. All eleven lockfiles match
`d5bd2b7` byte for byte. Maintenance notices remain for
chrono, paste and daemonize in the applicable locks. The Rust server uses
chrono for local-time certificate scheduling as well as dates. Both the Caddy
module with its release tags and the independent Go interoperability client
passed source-mode govulncheck. The original release gate combined reviewed IDs
from all four transport snapshots. One module could therefore satisfy the
review for a different module with the same advisory ID. Both test and release
workflows now query each exact module separately, reject empty scanner output
and fail on an advisory missing from that module's record. Regression tests
exercise shared IDs in both orders. The actual queries returned seven reviewed
records for x/net and zero for the other three versions. Four Rustls copies
matched all 120 packaged SHA-256 records and their recorded TLS patch. All
108 packaged files under `src` matched the complete upstream test tree. Using
that tree's original test certificates and binary fixtures, 555 Rustls tests
passed with the ring provider, TLS 1.2 and logging enabled. Eight upstream
Bogo/documentation cases remained skipped. The published crate omits those
fixtures, so directly running its library tests cannot reproduce this suite.

Ubuntu kernels running the matching Linux release binaries. The x86-64 and
arm64 release benchmarks in the earlier section ran natively. These Apple

63, 1200 and 1350 bytes. Caddy's no-SNI certificate selector uses its local
socket IP. An initial NAT fixture's certificate covered the Mac loopback
address and omitted the guest address. The named matrix uses separate relay
and origin DNS names, a certificate that also covers both test addresses, and
validates both Linux relay listeners with and without SNI. The counter service

### H3 UDP return path and packet size

A fresh macOS 27 NWConnection sent four numbered datagrams at 0, 50, 250
and 1000 ms without waiting for earlier responses. Two rounds compared an
immediate train, 500 ms of silence and a 64-byte priming datagram plus 500 ms.
All 48 server, size and timing combinations reached their expected Linux
origin counts. Rust returned all four 1400-byte echoes in five runs and three
in the sixth. Caddy returned zero of the 24 full-size 1400-byte echoes. Its
authenticated session accounting recorded 5600 bytes upstream and zero
downstream on each non-primed train, with zero quota drops. With priming,
only the 64-byte datagram returned. At 1200 and 1350, all eight primed
datagrams of each size returned, whereas immediate trains lost their first
one or two. The tests distinguish application admission, target arrival and
server enqueue from eventual delivery. [Numbered UDP packets and server counts](https://github.com/ArcCal/caddy-network-relay/actions/runs/44756390320).

Two controlled changes tested the QUIC size limit separately. Scheduling
ordinary probes immediately after authenticated H3 CONNECT-UDP helped the
500 ms idle 1200- and 1350-byte cases, but both immediate trials at each
size still lost the first packet and zero of 24 full-size 1400-byte echoes
returned. This early scheduling change was kept on the diagnostic branch.
[Authenticated early-probe comparison](https://github.com/ArcCal/caddy-network-relay/actions/runs/44757600652).

Caddy's supported unprivileged deployment documents a remaining tradeoff in
RFC 9298 section 6.1. It drops a target reply that cannot fit the QUIC
DATAGRAM. The connected UDP socket supplies no original IP header for the
ICMP quotation and the service has no raw-socket capability, so it does not
originate the recommended ICMP Packet Too Big feedback to the target. Targets
that depend on that signal can keep sending an oversized payload. The size
fix retains those privilege and framing boundaries.
[Caddy design decision](https://github.com/ArcCal/caddy-network-relay/blob/d7483b1fbe75b60af414ec043642b51ae5c43436/docs/design.md)
[RFC 4443 section 2.4](https://www.rfc-editor.org/rfc/rfc4443#section-2.4).

For a 1400-byte UDP payload the HTTP/3 flow ID and MASQUE Context ID made
the QUIC DATAGRAM data 1402 bytes in this test. On the unrestricted Linux
path, quic-go's ordinary packet search stopped with a confirmed packet size
of 1436. Its conservative payload estimate subtracted 37, so the usable limit
stayed at 1399. A three-byte shortfall prevented a whole 1400-byte echo. The
unmodified Go regression failed on both independent control runs. The final
candidate only refines the remaining discovery interval after the application
has actually requested an attainable size. Each increase still requires an
acknowledged path probe. The application continues to drop a datagram that
cannot fit at send time, and the regression verifies both the returning data
and a path fixture that discards outer UDP payloads above 1232 bytes. Four local repetitions
of both sizes on both paths passed. An instrumented Mac comparison returned
14 of 24 full-sized 1400-byte echoes versus zero on its control. In that
diagnostic the probe's own input guard rejected all 1401-byte inputs before
network I/O, so those twelve cases provide no path evidence. The clean
product candidate omits the numeric instrumentation and the early-probe

## CF MASQUE sustained traffic

The frozen test executable has SHA-256
`b2997af0ee7d3ad012e59375c2b1c4561ac02cb8efd1f51f8e4c59a12c036bd8`.
All 222 tracked CF MASQUE files and all 215 tracked parent source, vendor
and Cargo manifest/lock files matched the integrated candidate byte for byte.
The fixture uses an independent local WARP peer, forced H2 and forced H3,
six held TCP flows, six held UDP flows and independently checked TCP data.

The first 3900-second run exited zero after 3955.07 seconds of wall time.
The wrapper then rejected its evidence path because a directory symlink resolved
outside the test tree. The original rejection was retained. Replaying the
unmodified verifier with the identical binary, log and frozen source hashes
under a physical directory validated all 131 samples, 3926.55 measured seconds,
a minimum of 394 pings per held flow, one outer generation per transport and
zero reported queue drops. RSS rose from 117864 to 128792 KiB, peaking at

directories from the start. Its test and original evidence wrapper both

drops. RSS was 117672 KiB initially and 131896 KiB at the last sample and
peak. File descriptors ranged from 40 to 43 and ended at 40. The run confirms

## Deployment conditions still unmeasured

The named endpoint matrix exercised Apple's real per-session networking APIs.
A physical iPhone or Mac with an MDM-installed profile, its actual ISP or
cellular path, hardware sleep/wake and handover, the production Linux NIC
and its offload/queue settings, and real public Cloudflare WARP egress were
not measured. The local impairment, native Linux throughput, emulated Linux
interop and real macOS helper results describe different conditions. None
provides a general WAN throughput figure or an exclusion of every regression.

## Reproducing the test conditions

- On either supported Linux release architecture, use the exact candidate
  revisions above. Run `cargo test --locked` at the Network Relay root.
  The release workflow records the larger transfer limit and independently
  builds Linux arm64 and x86-64. [Release matrix](https://github.com/ArcCal/network-relay/actions/runs/44804285686).
- In `network-relay-cf-masque`, `bash scripts/test.sh` prepares the independent
  clients and exercises the local egress peer. `bash scripts/soak.sh` records
  the fixed binary, source identities and held H2/H3 connections. Both scripts
  use the project's test account and isolated local origin. [Variant tests](../network-relay-cf-masque/README.md).
- In Caddy, run `bash third_party/check-advisories.sh` from the repository root.
  Use the release workflow's reviewed Go source preparation and exact tags
  before running `go test -race -tags http2legacy,relay_tls9846_v1 ./...`.
  The installer checks accept a real compiled binary through `CADDY_REAL_BINARY`
  and `RELAY_TEST_CADDY`. [Final Caddy CI](https://github.com/ArcCal/caddy-network-relay/actions/runs/44799999391).
- On a disposable Mac, the native job builds and verifies the app, installs
  its launchd helper and invokes `network-relay-tun/scripts/test-native-helper.sh --capture`.
  The capture phase changes the runner's routes and DNS and verifies exact
  restoration. [Native TUN steps](../network-relay-tun/ci/macos-validation.yml).
- The half-close comparison at `3dc3985` builds the original implementation
  and three alternatives, verifies independent payload hashes and records
  both sockets during normal and paused reads. The companion commit
  `71cd3c9` runs the native Linux peer in the opposite half-close order.
  The privileged netem and TUN steps run inside disposable network namespaces.
  [Half-close comparisons and release checks](https://github.com/ArcCal/network-relay/blob/3dc3985c2b101d1cb78c4705209f3eef6aa59532/.github/workflows/warp-half-close.yml).
