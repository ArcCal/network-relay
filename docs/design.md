# Design

## 1. Apple's network relay

Since iOS 17, iPadOS 17 and macOS 14, Apple's operating systems have a built-in "Network Relay": the system hands matching connections to an HTTP proxy server to forward, with no VPN app needed. iCloud Private Relay uses the same kind of protocol.

There are three ways to configure it:

| Method | Applies to | This project |
|---|---|---|
| Profile payload `com.apple.relay.managed` | iOS 17+, macOS 14+; **can be installed by hand**, no supervision needed. Marked "deprecated" from iOS, macOS and visionOS 27 | **Uses this**. Generated by `network-relay profile` |
| Declarative device management (DDM) `com.apple.configuration.network.relay` | iOS/macOS/visionOS 27+; delivered through MDM, subject to the schema's enrollment/scope rules | Generates JSON with `profile --ddm`; device delivery not yet verified |
| Configured by an app with `NERelayManager` | The app's own relay configuration | Not covered |

"Deprecated" means Apple recommends moving to DDM; the schema does not mark the legacy payload as removed. A successful install, or Settings showing the relay as on, does not replace verifying actual traffic on a real device, which this project has not done yet.

### 1.1 Keys in the profile

From Apple's [Relay payload documentation](https://developer.apple.com/documentation/devicemanagement/relay) and `mdm/profiles/com.apple.relay.managed.yaml` in the [apple/device-management](https://github.com/apple/device-management) repository:

| Key | Meaning | What `network-relay profile` does |
|---|---|---|
| `Relays` | List of relay servers; several can be chained | One |
| `Relays[].HTTP3RelayURL` | "A URL or a URI template as defined in RFC 9298 for a relay reached over HTTP/3 that **proxies TCP and UDP using the CONNECT method**" | URI template `https://domain/.well-known/masque/udp/{target_host}/{target_port}/` |
| `Relays[].HTTP2RelayURL` | Same, over HTTP/2 | The same template |
| `Relays[].AdditionalHTTPHeaderFields` | HTTP headers added to every request | `Authorization: Basic ...` |
| `Relays[].PayloadCertificateUUID` | Client authentication with an identity certificate in the profile | `--identity file.p12`: a `com.apple.security.pkcs12` payload in the same profile, referred to by its UUID |
| `Relays[].RawPublicKeys` | Verify the server with fixed public keys instead of a CA | Not used (uses a public CA certificate) |
| `MatchDomains` | Only these domains and their subdomains go through the relay; when it and `MatchFQDNs` are both empty, everything does | `--match-domain` |
| `ExcludedDomains` | These domains and their subdomains do not go through the relay | `--exclude-domain` |
| `MatchFQDNs`, `ExcludedFQDNs` | Exactly matching domain names (iOS 18.4, macOS 15.4 and later) | `--match-fqdn`, `--exclude-fqdn` |
| `UIToggleEnabled` | Lets the user turn the relay off, default true (iOS/macOS 26 and later; the legacy payload supports it too) | `--ui-toggle-enabled true/false` |
| `AllowDNSFailover` | Allows falling back to the device's default system DNS, default false (iOS/macOS 26 and later) | `--allow-dns-failover true/false` |
| `RelayUUID` | Identifier for managed app routing, required for user enrollment; not supported on macOS | `--relay-uuid`; the app association is still configured in MDM |

The same settings exist as a declarative device management configuration, `com.apple.configuration.network.relay`, whose relays name an identity by `IdentityAssetReference` instead of a certificate payload. `network-relay profile --ddm` writes one as JSON (`Type`, `Identifier`, `ServerToken`, `Payload`) for an MDM server, with `--identity-asset` for the identity asset's identifier.

### 1.2 How devices use the relay

Combining Apple's documentation, [WWDC23 "Ready, set, relay: Protect app traffic with network relays"](https://developer.apple.com/videos/play/wwdc2023/10002/), the [NERelay](https://developer.apple.com/documentation/networkextension/nerelay) API documentation, and jedda's hands-on article [Beneath the MASQUE: Network Relay on Apple Platforms](https://jedda.me/beneath-the-masque-network-relay-on-apple-platforms/) with its accompanying [Envoy configuration](https://gist.github.com/jedda/62643893faffd9143f9587a12ca1db38):

- **TCP uses classic CONNECT**: `:method = CONNECT`, `:authority = target-host:port`, no `:protocol`.
- **UDP uses CONNECT-UDP** (RFC 9298): extended CONNECT, `:protocol = connect-udp`, with the path expanded from the URI template. On HTTP/3, UDP packets travel as QUIC DATAGRAMs.
- The Envoy configuration example enables classic CONNECT and CONNECT-UDP separately and can serve as an implementation reference; supporting the same protocols is not the same as being verified on real Apple devices.
- The relay URL may be just `https://host:port/`, in which case UDP uses RFC 9298's default template `/.well-known/masque/udp/{target_host}/{target_port}/`. This project uses that template by default and writes the full template into the profile, so both readings agree.
- **Host names carried in requests are resolved by the relay**: for example `CONNECT www.example.com:443`. Whether the device still uses local DNS depends on the system and on the match/failover policy, so it cannot be claimed that all DNS goes through the relay.
- The authorization header is the one written in the profile and is sent proactively with every request, without waiting for a 401/407 challenge. So the relay can pose as an ordinary website to requests that carry no credentials.
- Devices may query `https://relay-domain/.well-known/pvd` per [draft-ietf-intarea-proxy-config](https://datatracker.ietf.org/doc/draft-ietf-intarea-proxy-config/) (co-authored by Apple) to look for additional proxy configuration. This project answers 404 for missing files under `/.well-known/`, so devices use only the configuration in the profile.
- `NERelayManagerClientError` lists the errors a device may report: certificate expired/invalid/missing, DNS failure, server certificate expired/invalid, server disconnected, server unreachable and so on. What the server side controls is: a valid certificate with the right name, open ports and correct authentication.

### 1.3 Other implementations

Looked at during research: Envoy (the configuration above), quic-go's [masque-go](https://github.com/quic-go/masque-go) (CONNECT-UDP client and server, HTTP/3 only), sing-box's MASQUE client, Vincent-bin/masque-server (a CONNECT/CONNECT-UDP server aimed at Apple's relay and Surge), erlang_masque, and connect-ip-go (CONNECT-IP). mihomo/usque use Cloudflare WARP's proprietary variant, which is not compatible with the standard.

## 2. Protocol implementation

### 2.1 Request classification

| HTTP version | TCP tunnel | UDP tunnel |
|---|---|---|
| HTTP/3 | `CONNECT`, no `:protocol`, `:authority = host:port` (RFC 9114 §4.4) | `CONNECT`, `:protocol = connect-udp`, `:path` matches the template (RFC 9298 §3.4) |
| HTTP/2 | Same (RFC 9113 §8.5) | Same (RFC 8441 extended CONNECT) |
| HTTP/1.1 | `CONNECT host:port HTTP/1.1` (RFC 9110 section 9.3.6), the target in authority form only (RFC 9112 section 3.2.3; any other form names no target, and Host is not a fallback) | `GET path` + `Connection: Upgrade` + `Upgrade: connect-udp` (RFC 9298 section 3.2), answered with 101 |

Every other request goes to the decoy website. Malformed HTTP/3 requests (RFC 9114 section 4.1.2: a pseudo-header field twice or missing, `:scheme`/`:path` on a classic CONNECT, `:protocol` without CONNECT, and so on) are reset with `H3_MESSAGE_ERROR` before any of this, as h2 resets malformed HTTP/2 requests with `PROTOCOL_ERROR`. `:protocol` is an upgrade token and is matched without regard to case (RFC 9110 section 7.8), as `Upgrade` is on HTTP/1.1. Once authenticated, an extended CONNECT for another protocol (`connect-tcp`, `connect-ip`, `websocket`) gets 501, and a malformed UDP proxying request (RFC 9298 section 3.2, section 3.4: `:scheme` other than `https`; on HTTP/1.1 an `Upgrade: connect-udp` that is not a GET with `Connection: Upgrade`) gets 400; on HTTP/2 and HTTP/3 it is malformed, so the 400 is followed by a stream reset with `PROTOCOL_ERROR` or `H3_MESSAGE_ERROR` (RFC 9113 section 8.1.1, RFC 9114 section 4.1.2), which on HTTP/3 may discard the 400. `Upgrade` on HTTP/1.0 is ignored (RFC 9110 section 7.8). On HTTP/1.1 an invalid Host value gets 400 (RFC 9112 section 3.2), and a refused CONNECT, or a connect-udp upgrade answered with anything but 101, closes the connection, so that bytes sent after it are never read as further requests (RFC 9931 section 8, section 6.3).

### 2.2 Handling a request

1. **Classify**: not one of the requests in the table above → website. A UDP request whose path does not match the template → website.
2. **Authenticate**: a client certificate whose fingerprint belongs to a user; otherwise `Proxy-Authorization` first, then `Authorization`, both parsed as Basic. Failure → website (CONNECT gets 404). Authentication failures are logged at a bounded rate (the user name is escaped first, so log lines cannot be forged).
3. **Slots**: the user's tunnels have reached `max_tunnels_per_user`, or all tunnels `max_tunnels` → 503 (`connection_limit_reached`).
4. **Target**: for TCP, parse `host:port` from `:authority` (the port is required, IPv6 in brackets); for UDP, take `target_host` (IPv6 without brackets, colons percent-encoded as RFC 9298 §2 asks; a client that leaves them as they are, which a path may carry, still names the same address) and `target_port` from the template variables. Malformed → 400.
5. **Policy**: port in `blocked_ports` → 403 (`http_request_denied`); resolve the domain (5-second timeout, at most 256 lookups at once and 32 per user; a lookup holds its place until the system resolver returns, even after the timeout gave up on it); check every resolved address against `blocked_destinations` and the server's own addresses, IPv6 addresses carrying an IPv4 address also by that address; none left → 502 (`destination_ip_prohibited`).
6. **Connect**: TCP uses Happy Eyeballs (RFC 8305): in resolution order, alternating between the two address families, one more attempt every 250 milliseconds, moving on immediately when one fails, with `connect_timeout_secs` as the overall timeout. UDP creates a connected UDP socket (receiving only packets sent back by the target) and picks the first address that has a route.
7. **Respond**: 200 on success (101 for CONNECT-UDP over HTTP/1.1), with `Capsule-Protocol: ?1` for CONNECT-UDP. On failure, RFC 9209's `Proxy-Status: network-relay; error=...` with the status code §2.3 recommends for it: `dns_error` 502 (also for a name without addresses), `dns_timeout` 504, `destination_ip_prohibited` 502, `destination_ip_unroutable` 502, `connection_refused` 502, `connection_timeout` 504, `connection_limit_reached` 503, `http_request_denied` 403, `http_request_error` 400.

### 2.3 TCP relaying

- **HTTP/3**: the DATA frames on the request stream are the TCP data. When one side sends FIN (end of stream / TCP FIN), the other side's sending direction is shut down while the other direction carries on; the tunnel is done only when both directions have ended (half-close). If either side fails: the request stream is reset with `H3_CONNECT_ERROR` and the target side gets a TCP RST (`SO_LINGER=0`), as RFC 9114 §4.4 requires. When the user is deleted, `H3_REQUEST_CANCELLED` is used.
- **HTTP/2**: DATA, flow control and RST_STREAM are managed directly through h2, copying in both directions and passing on half-close; target TCP errors (including RST) explicitly send `CONNECT_ERROR`, and a client reset or user revocation sends RST to the target side.
- **HTTP/1.1**: hyper hands over the stream after CONNECT, which is copied in both directions with half-close passed on; on error the target side gets RST.
- After an HTTP/2 half-close, RST_STREAM is still watched for; on HTTP/3, STOP_SENDING and connection loss are watched for even while idle. While the response headers are blocked by flow control, user revocation can still cancel the established connection.
- Trailing HEADERS on CONNECT: HTTP/2 uses a `PROTOCOL_ERROR` stream error, HTTP/3 an `H3_FRAME_UNEXPECTED` connection error. Empty DATA does not mean FIN, and truncated DATA cannot be taken as a normal end.
- The buffer for reading from the target is 64 KiB. Bytes are counted as they are forwarded, so the statistics are accurate however the connection ends.
- Target connections turn off Nagle (the device's TCP has already coalesced packets) and turn on keepalive (from 2 minutes), so connections do not hang forever after the peer disappears.

### 2.4 UDP relaying

- Datagram format (RFC 9298 §5): context ID (variable-length integer) + UDP payload. Only context ID 0 is handled, others are dropped; an empty payload is valid, and one over 65527 bytes aborts the flow.
- HTTP/3 sends QUIC DATAGRAMs only when both HTTP's `SETTINGS_H3_DATAGRAM` and QUIC's DATAGRAM support have been negotiated (RFC 9297); otherwise, as on HTTP/2 and HTTP/1.1, it uses DATAGRAM capsules on the request stream.
- Capsules of an unknown type or unknown context are skipped as a stream, without the UDP size limit; for context 0, the UDP limit is checked as early as possible from the declared length. Malformations such as truncation abort the request stream; capsule requests forbid `Content-Length`, `Content-Type` and `Transfer-Encoding` (RFC 9297 §3.2–3.3).
- Target UDP sockets on Linux explicitly set the IPv4/IPv6 don't-fragment policy; packets larger than the path MTU are dropped rather than causing IP fragmentation (RFC 9298 §3.1).
- UDP packets from the target that are too large for one QUIC DATAGRAM are dropped, not sent reliably instead (otherwise QUIC inside QUIC would have the two congestion controllers interfere with each other).
- Packets are dropped when the queue is full or a single datagram is too large for the path (EMSGSIZE); ICMP Destination Unreachable (ECONNREFUSED, EHOSTUNREACH, ENETUNREACH on the connected socket), any other socket failure, or a closed request write side ends the flow (RFC 9298 §3.1). The forwarding loop limits how many packets it receives per round, and still responds to revocation and timeouts while waiting to send.
- The error code for an early end depends on the cause: malformed capsules or datagrams use `H3_MESSAGE_ERROR` / `PROTOCOL_ERROR`, a failed target socket uses `H3_CONNECT_ERROR` / `CONNECT_ERROR`, and device cancellation or user revocation uses `H3_REQUEST_CANCELLED` / `CANCEL`.
- Capsules queued for the device are limited to 16 and 128 KiB, so a few maximum-size UDP datagrams cannot make one flow hold much; more are dropped, as UDP allows.
- After a flow ends, the capsule write queue gets at most one second to drain; a write side that stays blocked is then reset, so no background tasks are left behind. On HTTP/3, the device's sending is stopped with `H3_NO_ERROR` when the relay ends a flow itself (idle timeout).
- Closed after `udp_idle_timeout_secs` with no packets in either direction (RFC 4787 requires NAT mappings to last at least 2 minutes; the default is 5 minutes). Closed immediately when the device closes the request stream.

### 2.5 HTTP/3 details

- Each QUIC connection has a single datagram reader, which hands datagrams to the matching UDP flow by the quarter stream ID in the datagram.
- When an HTTP Datagram arrives on a known non-UDP request, the request is reset with `H3_DATAGRAM_ERROR`; datagrams that arrive after the request's receive direction has closed (the device has sent FIN) or after the stream has ended are silently dropped (RFC 9297 §2.1).
- **Early datagrams**: RFC 9298 §5 lets the device start sending UDP packets after sending the request but before receiving the response (QUIC's first packet, for example). The relay may still be authenticating, so the datagrams have no matching flow yet. Each connection holds up to 64 such datagrams, within a 256 KiB byte limit, for at most one second (RFC 9297 §2.1: "on the order of a round trip"), and hands them over when the flow is set up; any beyond that are dropped first in, first out. Datagram payloads are copied out of the buffer QUIC received them in, so a queued datagram holds only its own bytes.
- Each request is parsed and handled in its own task, so a slow request does not hold up other requests on the same connection.
- **Frame sizes**: only DATA frames are streamed; any other frame is buffered whole before it is decoded. Frames of unknown types are discarded as they arrive (RFC 9114 section 9), a CANCEL_PUSH, GOAWAY or MAX_PUSH_ID longer than one varint is `H3_FRAME_ERROR` (section 7.1), and other frames over 64 KiB, twice the 32 KiB header limit, close the connection with `H3_EXCESSIVE_LOAD` (section 8.1). Previously a peer could declare a frame of any length and make the relay buffer it (vendored h3 fix).
- **Streams**: each relayed TCP connection and UDP flow of a device is one request stream, usually all on one connection, and UDP flows stay open until idle for minutes. A connection may open 100 streams at once (the minimum RFC 9114 §6.1 recommends) until one of its requests authenticates, then 1024 (`max_tunnels_per_user` still bounds tunnels per user). The lower first limit bounds what an anonymous client can make the relay hold, while a device's first burst of requests goes through.
- Windows and buffers scale with the connection's memory reservation (`limits::connection_memory`, 8 MiB, less on hosts under 64 MiB): a 1 MiB receive window per stream and 4 MiB per connection, a 2 MiB send window, and 256 KiB each of datagram send and receive buffer. The connection receive window holds four stream windows: data a device sends is released only as its destination accepts it, and connection credit also covers new requests (RFC 9000 section 4.1). With a connection window of two stream windows (version 1.5 and earlier), two uploads to destinations that stopped reading blocked every other tunnel and request on the connection. The transport idle timeout is 300 seconds (in practice the smaller of the two sides' values).
- **Path MTU**: relayed QUIC packets are at least 1200 bytes (RFC 9000 §14.1); with the outer QUIC header, DATAGRAM frame and context ID, they need about 1250 bytes of UDP payload. The connection starts at the 1200 bytes every QUIC path must carry, so the handshake works on any path, and DPLPMTUD (RFC 8899, RFC 9000 §14.3) probes up to 1452 bytes (a 1500-byte link with IPv6 and UDP headers) within the first round trips. Until a probe succeeds, or on a path that cannot carry more, datagrams too large to send are dropped and the device's own QUIC falls back to smaller packets, as on any path with a small MTU. A fixed larger initial MTU would instead lose the whole connection on such paths.
- **Shutdown**: on SIGTERM, GOAWAY on every connection carrying the first request ID not processed (RFC 9114 §5.2); later requests get `H3_REQUEST_REJECTED`; open requests get up to 5 seconds before `CONNECTION_CLOSE` with `H3_NO_ERROR`. GOAWAY travels on the control stream, which is flow controlled: sending it gets one second, so a client that grants no credit for it cannot keep a connection open (on shutdown, or when an idle connection is closed).
- **Cancellation codes** (RFC 9114 §4.1.1): a request the relay gives up on is ended in both directions with the same code: reset of the response side and STOP_SENDING for the request side. A request whose headers have not arrived within 10 seconds was not processed, so it gets `H3_REQUEST_REJECTED` and the client may retry it; one the client cancels while it is being authorized or connected, or whose user is revoked, gets `H3_REQUEST_CANCELLED`; tunnels end with the codes in §2.3 and §2.4. Previously the STOP_SENDING half lost its code whenever a read was pending (nearly always), and clients saw code 0, which HTTP/3 does not define (vendored h3-quinn fix).
- **Admission**: connections beyond `max_connections` or `max_connections_per_ip` are refused before the TLS handshake. When new handshakes arrive faster than 200 per second (after a burst of 400), or once half of `max_connections` is taken, clients must first prove their address with a Retry (RFC 9000 section 8.1.2), so spoofed sources cannot make the relay do handshake work or hold connection slots, which HTTP/2 and HTTP/1.1 share. A connection gets 10 seconds to finish its handshake. Accepting a connection reserves no memory: a connection reserves its windows from the shared budget only when it opens its first tunnel, so neither idle connections nor spoofed handshakes can use up what devices need (version 1.2 reserved them on accept, which let 64 idle connections from one address lock every device out of a 1 GiB server).
- UDP sockets request 8 MiB send and receive buffers; if the kernel limit is too small a message is logged, and `deploy/99-network-relay.conf` raises the limit.

### 2.6 HTTP/2 details

- `SETTINGS_ENABLE_CONNECT_PROTOCOL` (RFC 8441); without it, devices cannot send CONNECT-UDP.
- At most 256 concurrent streams (HTTP/2 announces the limit before any request authenticates, so it cannot be raised later as on HTTP/3), a 1 MiB receive window per stream and a 4 MiB connection window (four stream windows, for the reason given for HTTP/3), scaled down on small hosts; queued sends are limited to 64 KiB per stream. A PING every 30 seconds disconnects after 20 seconds without a reply. Both HTTP/2 and HTTP/3 limit request headers to 32 KiB.
- The website's answers drop the request body before responding (freeing its flow control credit) and send the page as slices of the website's own buffers.
- On SIGTERM, GOAWAY (RFC 9113 §6.8); h2 closes the connection once its streams end, or the process exits after 5 seconds.
- Connections over `max_connections` or `max_connections_per_ip` are closed as soon as they are accepted. A connection with no open request for `idle_timeout_secs` (30 seconds if none of its requests authenticated) is closed with GOAWAY.
- TLS offers both HTTP/2 and HTTP/1.1 (ALPN) and allows TLS 1.2, like an ordinary website. HTTP/3 uses only TLS 1.3.

## 3. Authentication

- **Hashes**: `network-relay passwd` generates 144-bit random passwords, which cannot be guessed, online or from a stolen hash, so they get a fast hash: PBKDF2-HMAC-SHA256 with 1000 rounds (`$pbkdf2-sha256$i=1000,l=32$salt$hash`, the same format the Caddy plugin uses). Passwords people choose (`passwd --stdin`) get Argon2id (19 MiB, 2 iterations, as OWASP recommends), whose parameters are bounded (at most 64 MiB, 10 passes, 4 lanes) so that a configured hash cannot make one check exhaust the server.
- **Who pays for a check**: every authenticated request carries the credentials. A request whose header is bound to its connection (it authenticated there before) or cached costs no hash. Only new credentials are checked, and those checks are limited: per client address (IPv4 address or IPv6 /64), about one per second after a burst of 30, and per connection, four at a time. Requests with the same new header wait for one check instead of each starting one, and waiting does not count against the connection's limit. Over the limits, the request gets the website, as for wrong credentials. So an attacker without credentials can make the server compute at most one cheap hash per second per address, and a device opening many tunnels with its credentials costs one.
- **Cache**: results are cached by request header: successes for 10 minutes after their last use, failures for 1 minute. The cache key is an HMAC-SHA256 of the request header (with a random key per start), so no passwords are kept in memory. The cache holds at most 4096 entries; once full, failures are no longer cached and cannot evict authenticated entries, so a batch of wrong credentials cannot force every device to recompute its hash.
- When the user list changes (reload), cached failures are dropped, and successes are kept only for users whose entry did not change; every active tunnel is told to check whether its user is still valid, and invalid ones are disconnected immediately. Results from verifications already under way cannot be written back into the cache; if the user was deleted or the password changed, such a result cannot pass authentication either, while users that did not change are unaffected by the reload. Changes are subscribed to before resolving the target and connecting, and the user is checked again after connecting and when forwarding starts, so no revocation is missed.
- **Expiry**: a user may have `expires`; from then on its credentials are refused, and its tunnels are closed at that moment.
- **Client certificates**: with `[tls] client_certificates`, TLS asks for an optional client certificate; any certificate whose handshake signature verifies is accepted at the TLS layer, and authorization compares its SHA-256 fingerprint with the configured users, so a certificate that matches no user is treated like no credentials (the website). `network-relay identity` creates the self-signed ECDSA certificate and a PKCS#12 file (3DES/SHA-1 key protection, which Apple devices require).
- The number of concurrent hash computations is capped (twice the number of CPU cores) and they run on threads of their own, so they never wait behind name lookups on tokio's blocking pool, nor lookups behind them; cancelling the HTTP request does not release a slot that is still computing. At most 4096 distinct credentials can wait for authentication, cleaned up on cancellation.
- An unknown user name still costs one hash computation (against a random hash of the same kind as the configured ones), so response times do not reveal which user names exist.

## 4. Camouflage

- Requests without valid credentials (including every CONNECT and Upgrade) are answered by the website. A 2xx on CONNECT means "tunnel established", so CONNECT gets a 404 with the home page.
- Missing paths return the home page (as single-page apps commonly do), so probing cannot find "a special path here". `/.well-known/` is the exception and gets an empty 404.
- Responses over TCP carry `Alt-Svc: h3=":443"`, like a website that offers HTTP/3.
- Status codes such as 403, 502 and 503, and `Proxy-Status`, are seen only by requests that passed authentication.

## 5. Security considerations

- **SSRF / internal network access**: by default private networks, cloud metadata services and the other special-purpose ranges are blocked (`blocked_destinations`), checking every address a domain resolves to, against DNS rebinding. IPv6 addresses that embed an IPv4 address (IPv4-mapped and -compatible, NAT64 `64:ff9b::/96`, 6to4, Teredo server and client) are also checked by that IPv4 address, and the local-use NAT64 prefix is in the default list. The server's own addresses, public ones included, are blocked as well (`block_own_addresses`, from the interface list, re-read at most every 10 seconds; if it cannot be read, everything is refused): a connection to the server's public address stays on the host and reaches services that a cloud firewall hides from the internet. Addresses that reach the host without being configured on an interface (some floating IPs, a load balancer) must be listed by hand.
- **Reloads** apply the new destination rules to open tunnels too: a tunnel whose connected address or port the new rules block is closed, like one whose user is removed.
- **Abuse**: port 25 is blocked by default; `max_tunnels` (sized from memory by default) limits the total number of tunnels and `max_tunnels_per_user` one user's share; optional per-user byte and packet rates; idle UDP flows are closed.
- **Connection floods**: connections are limited overall (by default from memory, 512 KiB each) and per address; QUIC connections over the limits are refused before the handshake, and Retry makes clients prove their address when handshakes arrive fast; idle connections are closed (unauthenticated ones after 30 seconds); the process raises its open-file limit to fit `max_tunnels` and `max_connections`. Connections reserve buffer memory only once they carry a tunnel, so a flood of connections cannot starve authenticated devices of it.
- **Slow readers**: a website or refusal response that makes no progress for 30 seconds because the client does not read it is abandoned (HTTP/2 `CANCEL`, HTTP/3 `H3_REQUEST_CANCELLED`, HTTP/1.1 closes the connection). Tunnels are exempt: their peers may pause as long as TCP allows.
- **Memory**: tunnels (512 KiB each), the connections that carry them and the website are admitted against a budget of half the memory; every queue a tunnel has is bounded in count and bytes. Kernel socket buffers are fixed per socket and bounded system-wide by Linux.
- **Logging under load**: logs go through a bounded queue to a separate thread, and lines are dropped rather than blocking the relay when the journal or disk is slow; failed authentications are logged at most about five per second with a count of those left out.
- **Relay loops**: a device cannot make the relay connect to its own addresses (above), and every layer requires authentication anyway.
- **Privileges**: under systemd it runs as its own user, `network-relay`, with only the `CAP_NET_BIND_SERVICE` capability, a read-only file system, and so on. It reads its configuration and a copy of the TLS key through group `network-relay`; the certbot deploy hook (`deploy/certbot-hook.sh`) renews the copy, since certbot's own key can be read by root alone. Profiles that root publishes are given to the owner of the `.publish` directory, so the relay can read them.
- **Logs**: passwords are never logged; `log_requests` shows only the user name from Basic credentials; user names supplied by clients are escaped before being logged.
- **Website files**: read into memory as a whole at startup and on reload. Only public files inside the site directory are included; after opening, the file actually opened is checked through `/proc/self/fd`, so a parent directory swapped for a symlink between the check and the open cannot expose files outside the site (the service runs as its own account).
- **HTTP/1.1 requests**: no `Host` or more than one `Host` gets 400 (RFC 9112 §3.2), as on an ordinary website.
- **Profiles**: with a password they contain Basic credentials in recoverable form (Apple's format dictates this); with `--identity`, they contain a PKCS#12 encrypted with a separate password the device asks for. `--publish` writes into the hidden `.publish` directory under a 144-bit random name; the website serves each such file once, within 15 minutes of its creation, and remembers served names across reloads. Saving, publishing and overwriting all go through atomic replacement with a mode-600 file and refuse symlink targets. The installer keeps no copy: the server holds only hashes, and `install.json` holds only the domain, port and user name. Profiles are not signed; signing with the administrator's own certificate (openssl `smime -sign`, or `security cms -S` on a Mac) is documented in config.md.

## 6. Code structure

A single crate, one program `network-relay`, five subcommands (`serve`, `passwd`, `identity`, `profile`, `check`).

| Module | Contents |
|---|---|
| `proto/` | Variable-length integers, capsules, datagram format, URI templates. No I/O, all unit tested. Copied from masque-vpn and changed to CONNECT-UDP semantics |
| `config` | Configuration file and validation |
| `auth` | Basic authentication, password hashes, certificate fingerprints, verification cache, attempt limits, expiry, user change notifications |
| `limits` | Token buckets, per-address connection counts, per-user tunnel counts and traffic budgets, the memory budget, the memory-based defaults for `max_tunnels` and `max_connections` |
| `identity` | Client certificates and PKCS#12 files for `network-relay identity` |
| `policy` | Target parsing and checks, refusal reasons and Proxy-Status |
| `connect` | Happy Eyeballs TCP connections, UDP sockets, on the host network or through an egress |
| `egress` | The interface through which a server built on this crate (network-relay-cf-masque) carries every tunnel's name lookups, TCP connections and UDP flows instead of the host network; network-relay itself uses none |
| `tunnel` | The CONNECT-UDP request stream (datagrams and capsules), independent of HTTP version |
| `server/` | `mod.rs`: request classification, authentication, opening targets, connection statistics, reload, `run`; `over_h3.rs`: QUIC and HTTP/3, datagram dispatch; `over_tcp.rs`: HTTP/2 and HTTP/1.1; `h2_stream.rs`: HTTP/2 byte streams, flow control and explicit resets; `pump.rs`: moving TCP and UDP data |
| `web` | Decoy website |
| `certs`, `tls` | Certificate loading, periodic rereading, rustls configuration |
| `profile`, `private_file` | Generating `.mobileconfig` files and DDM declarations, and saving them atomically with private permissions |
| `check` | Self-check client (HTTP/3, HTTP/2, HTTP/1.1), also used by the integration tests |
| `cli` | The `passwd`, `identity`, `profile` and `check` commands, shared with network-relay-cf-masque |
| `logging` | Non-blocking logging (optionally split into hourly files) |
| `sys` | Open-file limits, socket options |

`auth`, `certs`, `tls`, `web`, `logging` and `proto` were originally copied from [masque-vpn](https://github.com/ArcCal/masque-vpn) and then modified. The two projects do not share code and are released independently.

Dependencies: tokio, quinn (QUIC), h3 / h3-quinn / h3-datagram (HTTP/3, pinned to a commit with CONNECT-UDP support), h2 (HTTP/2 server), hyper (HTTP/1.1 server and HTTP client), rustls (ring), argon2.

`h3` and `h3-quinn` keep the source and licenses of the same upstream commit in `vendor/`, patched only for request and frame validation, request rejection, GOAWAY identifiers, cancellation notifications and stream error codes, plus client-only extensions used by network-relay-cf-masque's WARP egress, which a server never uses. See `PATCH.md` in each directory for the exact differences and when the patches can be removed. They have not been replaced with a different protocol implementation.

## 7. Interoperability tests

The automated integration tests check TCP/UDP round trips, half-close, revocation and concurrency over real TLS/QUIC connections, and also check HTTP/2 `CONNECT_ERROR` / `PROTOCOL_ERROR`, HTTP/3 `H3_DATAGRAM_ERROR`, capsule fallback when datagrams were not negotiated, large unknown capsules and empty UDP payloads. The automated no-fragmentation check reads the IPv4/IPv6 socket options; packet capture on a low-MTU link is not covered yet.

The method, specification sources and reproducible results of the most recent full review are in the [review record](review-2026-10-05.md) (the one before it: [2026-10-01](review-2026-10-01.md)). `tests/interop/masque-go` repeats the HTTP/3 checks with quic-go and masque-go against a running relay. The historical interoperability record of the first release is kept below; the historical results are not to be taken as re-verified in those reviews.

Besides `cargo test`, the following tests were done by hand before the release (relay on the local machine at `relay.test:8443`, private CA):

**curl (CONNECT over HTTP/1.1 and HTTP/2, credentials in `Proxy-Authorization`):**

```bash
curl --noproxy '' -p -x https://relay.test:8443 --proxy-cacert ca.pem \
  --resolve relay.test:8443:127.0.0.1 --proxy-user alice:password http://127.0.0.1:18080/
curl ... --proxy-http2 ...
```

Result: both versions got the web page; a wrong password got `CONNECT tunnel failed, response 404`; port 25 and `10.0.0.0/8` got 403.

**quic-go masque-go v0.6.0 (CONNECT-UDP over HTTP/3, credentials in `Authorization`):** a small Go program connects to the relay with `masque.Transport` and sends and receives datagrams through a UDP echo service.

Result: several hundred datagrams each of 60, 1200 and 1300 bytes all came back unchanged; the response carried `Capsule-Protocol: ?1`; a wrong password or no credentials got 404; `10.0.0.1:53` got 403 and `Proxy-Status: network-relay; error=destination_ip_prohibited`.

**`network-relay check`**: passed on all three HTTP versions against local targets and the real internet (reaching `example.com:80` through the relay and querying DNS at `1.1.1.1:53`).

**Privileges**: with `setpriv` keeping only `CAP_NET_BIND_SERVICE`, the relay could read a mode-600 private key and worked normally on port 443.

**Not done yet**: tests on a real iPhone or Mac.

## 8. Possible future work

- After verifying on real devices, adjust to their actual behavior (`log_requests` exists for this).
- `connect-tcp` ([draft-ietf-httpbis-connect-tcp](https://datatracker.ietf.org/doc/draft-ietf-httpbis-connect-tcp/)): add it once devices start using it. The h3 library in use does not recognize this `:protocol`, so the library has to be changed first.
- Per-user traffic statistics.
- Certificate authorities and revocation for client certificates (today they are pinned by fingerprint).
- `next-hop` in `Proxy-Status` on successful responses (the address actually connected to).
