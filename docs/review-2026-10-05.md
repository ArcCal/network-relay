# 2026-10-05 standards and interoperability review

This round reviewed the whole relay again against the normative texts and against independent client implementations, keeping the existing design: classic CONNECT for TCP and CONNECT-UDP (RFC 9298) for UDP over HTTP/3, HTTP/2 and HTTP/1.1, as Apple's Network Relay uses them; the decoy website; authentication; reload; profiles. No user-facing feature was added. The findings below are fixed and covered by regression tests; this is not a certification of conformance with every RFC clause or every Apple OS version, and real Apple devices were again not available.

## Sources

The RFC Editor's site could not be reached from the review environment, so the published sources in the working groups' repositories were read instead (the same commits as the 2026-10-01 review where they overlap):

- RFC 9298 and RFC 9297: `ietf-wg-masque` drafts at the commits named in the [2026-10-01 record](review-2026-10-01.md).
- RFC 9114 and RFC 9000: `quicwg/base-drafts` at `0921ecf1`.
- RFC 9113: `httpwg/http2-spec` at `670dbedf`.
- RFC 9110, RFC 9112, RFC 8441, RFC 9220, RFC 9209: `httpwg/httpwg.github.io` (`specs/rfc*.xml`).
- Apple: the `com.apple.relay.managed` schema in `apple/device-management` (branch `release`), and the NetworkExtension documentation for `NERelay`, `NERelayManager` and `NERelayManagerClientError` (developer.apple.com JSON). `NERelay`: "Relay servers are secure HTTP proxies that allow proxying TCP traffic using the `CONNECT` method and UDP traffic using the `connect-udp` protocol defined in RFC 9298"; `additionalHTTPHeaderFields` are sent "as part of `CONNECT` requests". This matches the relay's design (classic CONNECT for TCP, not `connect-tcp`).

## Findings and fixes

| Finding | Specification | Fix and regression test |
|---|---|---|
| When the relay ended a request or tunnel early, the client got STOP_SENDING with code 0, which HTTP/3 does not define, instead of the intended code (`H3_REQUEST_CANCELLED`, `H3_CONNECT_ERROR`, `H3_DATAGRAM_ERROR`, ...). h3-quinn moved the QUIC receive stream into a stored future while a read was pending and only remembered a `stop_sending` for when the read completed; the stream was nearly always dropped first. The reset of the response side carried the right code, which is all the earlier tests looked at | RFC 9114 §4.1.1, §4.4 | Vendored h3-quinn polls quinn's cancel-safe `read_chunk` in place, so `stop_sending` reaches the stream at once (`vendor/h3-quinn/PATCH.md`). `http3_aborted_tunnels_stop_the_client_with_the_abort_code` checks the codes of a datagram on a TCP tunnel and of revoked TCP and UDP tunnels; it fails with code 0 on the old transport. h3's own suite (241 tests, which compile the vendored h3-quinn) passes |
| A request the client cancelled while it was being authorized or connected was dropped, which also stopped the client's sending with code 0 | RFC 9114 §4.1.1 | Cancelled with `H3_REQUEST_CANCELLED` in both directions: `http3_request_the_client_cancels_while_connecting_is_cancelled_both_ways` (a destination with a full accept queue stalls the connect) |
| The 431 answer to request headers over 32 KiB was followed by dropping the stream: STOP_SENDING with code 0 | RFC 9114 §4.1 (`H3_NO_ERROR` when the server needs no more of the request) | Vendored h3 stops the request side with `H3_NO_ERROR` and finishes the response: `http3_request_headers_over_the_limit_get_431_and_no_error_stop` |
| A request whose headers did not arrive within 10 seconds was dropped: a FIN and no response, which the client reads as a truncated response | RFC 9114 §4.1.1 ("rejected": `H3_REQUEST_REJECTED`, may be retried) | Vendored h3 `RequestResolver::resolve_request_before`: `http3_request_whose_headers_never_arrive_is_rejected` |
| GOAWAY was awaited without a bound. It travels on the control stream, which is flow controlled: a client granting it no credit kept a connection the relay was closing (idle or shutting down), and its connection slot, as long as it sent keep-alives | RFC 9114 §5.2, §6.2.1; RFC 9000 §4.1 | One second for GOAWAY, then the connection is closed anyway: `http3_goaway_without_control_stream_credit_still_closes_the_connection` (the client grants exactly the 31 bytes of the relay's SETTINGS preamble) |
| `:protocol` was compared case-sensitively, so `CONNECT-UDP` got 501 | RFC 9110 §7.8 (upgrade tokens are case-insensitive; recipients SHOULD compare so), RFC 8441 §4 | `Kind::of_connect` unit test; `connect_udp_protocol_token_is_matched_without_case` over HTTP/3 and HTTP/2. The vendored h3 check of `TE: trailers` is case-insensitive likewise (RFC 5234 §2.3) |
| A CONNECT-UDP path naming an IPv6 target with unencoded colons got the website's 404 | RFC 9298 §2 (clients MUST encode); RFC 3986 §3.3 (`:` is a path character) | Accepted; the target is still validated: `unencoded_ipv6_colons_are_tolerated`, `connect_udp_targets_with_unencoded_ipv6_colons_are_understood` |

Checked and left as they are, with the reason:

- HTTP/2 refusals end with `RST_STREAM(NO_ERROR)` after the complete response. RFC 9113 §8.1 allows this and forbids clients to discard the response; curl 8.5.0 reports it as a receive failure, curl 8.14.1 (2026-10-01 review) shows the status.
- Kernel TCP socket buffers stay fixed per socket (512 KiB client, 1 MiB target), as documented in `docs/config.md`; they bound per-connection kernel memory at some cost in throughput on long paths. A tuning choice, not a defect.
- A CONNECT on HTTP/1.1 propagates half-close in both directions rather than closing both sides at the first FIN (RFC 9110 §9.3.6); HTTP/2 and HTTP/3 define half-close explicitly, and the relay treats all three alike.
- `connect-tcp` (draft-ietf-httpbis-connect-tcp) stays unimplemented: Apple documents classic CONNECT for TCP.
- `cargo audit` (RustSec, 1290 advisories): no vulnerable, unmaintained or yanked dependency.

## Verification

Linux x86_64, Rust 1.97.0, no IPv6 in the environment (the wildcard listener fell back to IPv4, as designed).

- `cargo fmt --check`; `cargo clippy --locked --all-targets -- -D warnings`.
- `cargo test --locked` and `cargo test --locked --release`: 153 unit tests, 64 integration tests over real TLS, QUIC, TCP and UDP. The integration tests ran 6 times in a row, then 3 rounds of 4 concurrent runs, all passing. One of the new tests failed in the first full runs: it finished its CONNECT-UDP stream, which ends the flow, before checking that the flow was open. It was corrected before these runs.
- Vendored h3: `cargo test --all-features` (241 tests and 9 doctests), run over IPv4 because its harness binds `[::]`.
- Deployment: `python3 -m unittest discover -s tests -p test_deploy.py` (34 tests), `bash -n deploy/install-debian13.sh`.
- Independent clients against the release binary on a local deployment (private CA, `relay.test`):
  - quic-go v0.63.0 and masque-go v0.6.0 (`tests/interop/masque-go`): CONNECT-UDP with 1, 60, 1200 and 1300-byte datagrams (50/50 echoed each), `Capsule-Protocol: ?1` on the response; classic CONNECT carrying 1 MiB each way with half-close; wrong credentials get 404; port 25 gets 403 `http_request_denied`, a closed port 502 `connection_refused`, an unknown name 502 `dns_error`.
  - curl 8.5.0: CONNECT over HTTP/1.1 (200, wrong password 404, port 25 403) and HTTP/2 (200); the website over HTTP/2.

To repeat the Go check: run a relay that allows 127.0.0.1 (`blocked_destinations = []`, `block_own_addresses = false`), then `go run . -relay 127.0.0.1:8443 -name relay.test -ca ca.pem -user alice -password ...` in `tests/interop/masque-go`.

## Not covered

Real iPhones, iPads and Macs; MDM delivery; IPv6 paths (none in the environment); packet capture on a low-MTU link; long-running wide-area load.
