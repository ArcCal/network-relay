Date: 2026-10-11. This is a user-supplied Mac log, not a cloud test. Times are
UTC. Native lines (`native:`) have one-second resolution; core lines have
microseconds. Endpoint addresses, the certificate name, destination addresses
and credentials are not reproduced.

## Native facts now observed

1. **The group owns stream 0.** Every `Native QUIC group ready` line reports
   `groupSID=0`.
2. **Requests use SID 4.** Every CONNECT and CONNECT-UDP request is on
   `SID=4 requestedDirection=bidi`; the client's control and QPACK streams
   are SID 2/6/10; the server's are SID 3/7/11/15.
3. **The group is the first object to fail.** Each EINVAL appears first as
   `WARN native: Resource <group> failed: POSIXErrorCode(rawValue: 22)` for a
   QUIC group resource, followed by the h3 driver ending and the flow or
   session failing.
4. **The timing matches a ten-second server deadline on stream 0.**

All seven failures occur 10.36–11.60 s after the group's first request. That is

## Interpretation

Established natively: the group owns SID 0, requests use SID 4, the group
object fails first with EINVAL, and the failure tracks each group's first
request by about ten seconds. Combined with the server source and emulator
results, the supported chain is:

1. The idle group-owned stream 0 is implicitly opened at the server.
2. The server's ten-second header deadline resets it.
3. Network.framework reports the reset as a failure of the whole group.

What is still unobserved is the server-side event: no server log was supplied,
and the deployed server and revision behind `gcp` are not pinned. The client
cannot send on stream 0 through `NWConnectionGroup`, so no change confined to
the current group API avoids this.

## Other observations, not caused by stream 0

- Many SOCKS flows on all three transports end with POSIX 54 shortly after
  `SOCKS CONNECT ready`. They occur equally over HTTP/1.1 and HTTP/2, so they
  are not specific to QUIC. Their source (local application or destination)
  is not determined.
- At 14:15:05Z, inbound streams SID 7/11/15 of one group report
  `Native stream receive queue overflow`. This is unexplained and recorded for
  follow-up.
- The first HTTP/2 attempt timed out at 10 s with TLS never ready; the retry
  succeeded. QUIC groups frequently show a transient POSIX 50 waiting state
  before readiness.

## Server repair

Server changes were later permitted. Both relay servers now start the HTTP/3
header deadline at a request stream's first byte, so the unwritten stream 0 is
left open instead of being rejected after ten seconds. Streams with partial
headers are still rejected as before. Unwritten streams do not count as
requests for the idle timeout and stay bounded by the QUIC stream limit.

| Server | Commit | Change |
| --- | --- | --- |
| network-relay | `9821c4f` | The request task waits for the stream's first byte (vendored h3 `RequestResolver::wait_for_data`) before counting the request and applying `HEADER_TIMEOUT`. |
| caddy-network-relay | `ef04df6` | The quic-go fork's `HandleRequestStream` peeks one byte before tracking the stream, taking a header slot or setting `ReadHeaderTimeout`. |

Tested in this environment (Linux, no Network.framework), 2026-10-11:

- `Core/tests/idle_stream_zero.rs` against both rebuilt servers:
  `stream0=[]` 13 s after admission (before: STOP_SENDING and RESET_STREAM at
  10.01 s). The UDP echo works before and after the deadline.
- The unchanged `real_server_matrix` passes against both over HTTP/1.1,
  HTTP/2 and HTTP/3.
- network-relay: new test `http3_unwritten_request_stream_is_left_open`; all
  217 existing unit and integration tests, including the partial-headers
  rejection test; the interop suite (masque-go and curl clients).
- caddy-network-relay: new test `TestH3UnwrittenStreamIsLeftOpen`, which fails
  without the change with code 269; the full suite with the race detector; the
  upstream quic-go http3 tests with the patch.

Not yet confirmed natively. Deploy a fixed server, force HTTP/3 at Detailed
logging, and check that no `WARN … Resource <group> failed: … 22` follows the
first request by about ten seconds, and that sessions stay up for at least ten
minutes.
